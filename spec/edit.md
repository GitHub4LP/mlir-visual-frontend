# 编辑代数与增量查询 v0

实现：`model/edit.py`。检验：`model/edit_test.py`（`PYTHONPATH=model python3 model/edit_test.py 40 12`，约 20 秒）。
这一层回答正确性标准 (3)：前端每做一次编辑，能推导出什么、代价多大、诊断和补全的依据是什么。

## 1 全性：洞是一等的 op
- 未连接的端口 = 连到一个 `edit.hole`。洞的值和毒值标志是自由变量。
- 因此**每个编辑中间状态都有 Schema**：它对洞参数化，和复合 op 对输入端口参数化是同一回事。这里参照 Hazel 的类型化洞（Omar 等，POPL 2017、ICFP 2019）。
- 删除不会被拒绝：被删节点的每个使用都改连到一个新洞。
- 编辑操作都是全函数：insert / delete / rewire / disconnect / fill / set_prop / set_op。

## 2 组合律
- **L20 连接洞 = 项代换。**
  - 把洞 h 连到值 v，等于在已有摘要里做代换 h ↦ v 的项（含毒值标志），不需要重推导。
  - 前提：v 支配洞的所有使用。在顶层 SSACFG 中，这个前提已经蕴含“v 不依赖 h”，所以不会成环。只有在 Graph 区域里才需要单独检查成环（实现中按项的出现做了检查；检验中实际排除数为 0，与这一推理一致）。
  - 检验：168/168 个候选，代换结果 ≡ 连接后重推导的结果。
- **L21 增量 = Merkle 键 + 指纹早截断。**
  - 定义的缓存键 = 定义名 + 体的规范序列化 + 各被调定义的**指纹**。
  - 指纹是摘要（输出项、UB、公理、效应、结构摘要与诊断）在端口规范改名、新变量按出现顺序改名后的哈希。
  - 所以改了体、但摘要不变时（死代码、`x+0 → x` 等能被化简掉的改动），依赖者直接命中缓存。
  - 语义截断（可选）：指纹不同但 z3 判定等价时，依赖者沿用旧指纹（Salsa 的 backdating）。代价是每个变化的定义多做一次证明。
- 判据：每一步编辑后，增量结果（结构诊断、效应、值层、caps、Pre）≡ 清空缓存后的全量推导。
  - 语法截断：480 次编辑，0 不一致；
  - 语义截断：240 次编辑，0 不一致。

- **预言机层的对应（第 20 轮，modular.md §9 L45）**：隔离单元的缓存键 = 子树 + 外壳 + 被引用声明；被引用声明（func.func 为名字 + function_type）就是指纹。失效集 = dirty ∪ 声明变了的单元的引用者，可在编辑点局部算出；12958 次真实 IR 编辑，可靠性违例 0、增量 ≡ 全量。

## 3 编辑 → 失效
| 编辑 | 结构层 | 值层 / 效应层 | 依赖者 |
|---|---|---|---|
| insert / delete / rewire / disconnect / fill | 局部义务（structure.md 的依赖表） | 所在定义重推导 | 只在指纹变化时重推导 |
| set_prop / set_op | 该节点的 R*（变化 op 时） | 所在定义重推导 | 同上 |
| 连接洞（只做查询，不提交） | 支配 | L20 代换，不推导 | 不涉及 |

- 实测：每次编辑平均重推导 1.0–1.75 个定义（共 3 个）。依赖者中有 64% 被语法截断省掉（302/470），多数是死代码上的编辑。
- 语义截断在 240 次编辑中额外截住 36 次：摘要语法不同、但语义等价。
- 定向用例：`a^b → (a|b)−(a&b)`，语法截断要重推导 2 个定义，语义截断只要 1 个；`x+0 → x` 两种截断都只要 1 个。
- 粒度：定义内部不再细分。推导 3 个定义约 6 ms，caps 查询约 4 ms。z3 的项本身是 hash-cons 的，重建很便宜，代价主要在查询上，所以查询要按指纹缓存。大型定义需要按区域细分，留到以后。

## 4 诊断与补全的依据
- 补全：洞 h 的候选 = 在第一个使用处可见、类型相符的值。每个候选用 L20 代换后分为三类（输入非毒值时）：
  - **安全**：一定不 UB；
  - **有条件**：UB 取决于输入；
  - **必然 UB**：一定 UB。
  - 检验：168 个候选中安全 93、有条件 66、必然 UB 9；分类与连接后重推导的分类 168/168 一致。
  - 编辑器据此排序：安全的排前面，必然 UB 的标红。
- 诊断：结构诊断按节点 id 给出（R*、S*），值层诊断是 Pre，不变式诊断见 loops.md。

## 5 检验抓到的两个缓存键错误
- 查询缓存原先只用指纹做键。指纹与命名无关，而 Pre 是用本定义的端口变量写的，于是摘要相同的两个定义会互相拿到对方的 Pre。200 次编辑中有 27 次结果不一致。
- Schema 缓存的键原先没有定义名，存在同样的潜在问题。
- 教训：**语义身份**（与命名无关，用来截断）和**呈现身份**（带名字，用来给出结果）必须分成两层键。

## 6 已知边界
- 编辑只作用在定义的顶层块上；区域内部（scf.if/for 体）的编辑还没做。
- 签名变更（改端口）在调用点只有结构检查兜底，还没有专门的传播规则。
- `ub.poison`、load 产生的新变量在指纹里改名后视为相同。这对截断是可靠的，但同一复合 op 的多个实例之间仍然共享这些变量（此前已有的限制）。
- 与 Adapton、Salsa、Build Systems à la Carte 的关系：这里是带早截断的按需记忆化，依赖由 Merkle 键隐式给出，没有显式的依赖图。
