# 名字即语义身份（第 27 轮）

**问题。** 模型里有很多东西按名字共享：z3 常量、未解释函数、注册表 REG。z3 会把同名同 sort 的项当成同一个。所以“名字相同 ⇒ 语义相同”是一条隐含的可靠性前提。第 26 轮已经说明，随机证伪看不到“不在文本里的语义来源”（L18 漏掉了参数）。本轮把所有按名字共享的地方逐项清点一遍。

## 1 清点表

| 位置 | 名字 | 旧状态 | 处置 | 检验 |
|---|---|---|---|---|
| 循环摘要 UF | `loop_<canon>` | 漏参数、语义开关（第 26 轮） | L18′：参数作实参，`sem_tag` 进名字；体内有洞时再加所属定义 | loopsum U0–U3 |
| **编辑洞** | `hole.{hid}` 常量 | **不可靠**：与环境无关，也不区分所属定义 | L20′：`hole.<定义>.<hid>` 是未解释函数，作用于此处已定义的全部值 | names N1 |
| 洞在循环摘要体内 | — | **不可靠**：L20 代换看不进摘要，会“证明” fill(1) ≡ fill(0) | `subst_fill` 拒绝（ValueUnknown）；`complete()` 改为真填后重推导 | N1c |
| **端口占位项** | `{name}.{p}` | **不可靠**：端口重名时两个端口共用一项，会“证明” x == y；名字也不单射（定义 `a.b` 的端口 c 与定义 `a` 的端口 b.c 同名） | 重名则拒绝；名字改为长度前缀 + 位置 | N2、N4 |
| **REG** | op 名 | **不可靠**：复合 op 与原生 op 同名时，会静默覆盖原生语义 | 拒绝，不登记（复合 op 覆盖复合 op 仍允许：表示新版本） | N3 |
| 复合 op 参数常量 | `{name}.${nm}` | 与 defs.derive_params 共享这一命名（契约）；只在调用点没给参数时才会悬空 | 保留，列为风险；重名参数已拒绝 | — |
| Ctx.env | SSA 名 | 每次推导独立；兄弟区域重名属于顺序覆盖，不影响结果 | 无问题 | — |
| fv() / FreshConst | 全局计数 | 唯一 | 无问题 | — |
| Workspace 的 Merkle 键 | 定义名 + 序列化 + 被调指纹 | 已含名字 | 无问题 | edit E1 |
| fingerprint 的 `H{i}`/`P.{nm}` | 只作字符串 | 不进入任何查询 | 无问题 | — |

## 2 洞的语义（L20′）
- 洞的最终内容可以连到任何作用域内的值，所以它是**环境的函数**，不是常量。这与 Hazel 的闭包语义一致。
- 实参取“此处已定义的全部值”。这是作用域的超集：实参越多，能认定相等的情况越少，所以只会更保守。
- 作用域内的值本身可能是非确定的（load、有效应的循环），它们也作为实参传入。
- 正对照：同一定义、同一实参调用两次，仍可证相等。
- 反例见证：填 h:=x 后，JIT 执行 main(1,2) 得 0，main(3,3) 得 1。旧实现在洞态下会“证明”两者恒等。

## 3 教训
- 新增任何按名字共享的项，都必须回答两个问题：名字编码了哪些语义来源？是否单射？
- 冲突时一律拒绝，不覆盖。
- 这一条记为定律 L54。
