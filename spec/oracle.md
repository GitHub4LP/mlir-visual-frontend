# 预言机层（第 10 轮）：类型判定的三层分工接入 core

实现：`model/oracle.py`（常驻、隔离的 MLIR verifier 子进程；core 图 → MLIR 通用形式；诊断按 `loc("节点")` 归位；按文本缓存），以及 `core.typecheck`（判定次序）。
检验：`model/oracle_test.py`，运行 `PYTHONPATH=model python3 model/oracle_test.py 1000`，约 2 分钟。

## 1 判定次序（core.typecheck）
1. **自动签名（odssig）。** 它对一切 op 是上近似（L29），所以它的拒绝是终判；对 auto 账目它是精确的（L28），auto op 不再交给别的层。
2. **预言机。** 只在两种情况下调用：体内有 declared/unknown 账目的 op，或某个端口组无法唯一绑定。此时整个体交给同一提交的 MLIR verifier，结论是终判。
3. **人工精度签名（typesig）。** 只在预言机不可用时使用，诊断标注“未经预言机”。预言机不可用的情形：体内有 MLIR 不认识的 op（复合 op）、core 的简写形式、符号常量、抽象类型、多块体。

### 纠正第 7 轮：人工签名不能当权威
随机图里出现了 `arith.subi(vector<i32>, vector<i32>)`，MLIR 接受，第 7 轮的人工签名却拒绝了。原因有两个：
- 人工字典的端口约束沿用了 llvm main 的写法，把 vector 限定为秩 > 0；
- 它的检验类型池里没有 0 维向量，所以这个错误从没被测到。

由此定下规则：**人工声明只能作为被审计的对象，不能作为权威。**预言机可用时它不参与判定；预言机不可用时才用它，并在线记录它与预言机的分歧（`TC_STATS`）。

### 发射器的忠实性守卫
发射器宁可让预言机不可用，也不发出不忠实的文本。否则 MLIR 拒绝的是我们的翻译，而不是用户的图。
- core 参数只翻译登记过的：nsw/nuw 翻成 `overflowFlags`，`predicate`，具体常量 `value`；其余参数一律不发射。
- op 的必需属性必须都已发射，分段 op 必须带分段；core 的 `tensor.extract_slice` 省略了 static_* 属性，因此被拒发。
- 符号常量（模式变量、复合 op 参数）、抽象类型（core 的 `memref`）、多块体：不发射。
- 区分两类失败：诊断全部落在 `loc("节点")` 上的是校验拒绝；带文件行列位置的是语法错误，记为发射缺陷，不算类型结论。（`Module.parse` 解析后会立即校验，两类失败都以解析异常的形式出现。）

## 2 检验结果（987 个随机直线图，1–4 个节点，覆盖 11 个方言中可参与差分的 223 个 op）
| 检验 | 结果 |
|---|---|
| O1 符号层 + 预言机 ≡ MLIR | **987/987** |
| O1 只用符号层 | 一致 924，误收 63，**误拒 0**（L29 在图上成立） |
| O2 无需问预言机的图 | 853/987：398 个全是 auto，其余由符号层先拒；实际调用预言机 134 次 |
| O2 typecheck 含一次预言机调用 | 中位约 670 µs；同一个体再查一次走缓存，约 73 µs |
| O3 符号层通过、MLIR 拒绝的图 | 200/200 的诊断落在节点上，并且都落在 declared/unknown 节点上，附 MLIR 原话 |
| O4 崩溃隔离 | 好→崩溃→好：ok、crash、ok；子进程自动重启 1 次，之后的结论正确；同一崩溃例在 core 里被符号层先拒，不会交给预言机 |
| 发射缺陷 | 0（O1）；回归测试中发现的 3 类缺陷已用守卫消除 |

- 回归：core、shape S6 421/421、transform、loop、edit 增量 ≡ 全量、typesig、compsig 全部通过。core 回归中预言机共调用约 1000 次，人工签名的误拒与误收均为 0。

## 3 组合律
- **L30 分层判定精确。** 预言机可用时，core.typecheck ≡ MLIR verifier；符号层的拒绝 ⊆ MLIR 的拒绝。
- **L31 诊断归位。** 预言机的拒绝总能落到具体节点，而且只会落在符号层管不到的节点（declared/unknown）上。

## 4 代价与对前端的意义
- 670 µs 里主要是进程间往返（JSON 加管道）。MLIR 原生校验本身约 3–15 µs，在 WASM 里同进程运行时可以省掉这部分往返。
- 预言机只回答具体实例，不提供候选、端口投影、Φ。这些查询仍由符号层负责：它是上近似，所以候选不会漏，但可能多出 declared op 的非法选项，选中后由预言机给出 MLIR 原话。
- 缓存键目前是文本哈希。接到 edit.md 的 Merkle 键之后，编辑只会让被改动的定义体重新查询。

## 5 缺口
- 预言机还不覆盖带 region/后继的 op 和多块体：发射器只处理单块直线体。
- core 的简写形式（切片 op 等）和符号参数需要先降级才能交给预言机。复合 op 实例要内联后才能交给预言机（compsig C1 已有内联发射，尚未并入 core）。
- 参与差分的必需属性仍只有 I64Enum 一种。

# 第 11 轮：预言机覆盖区域、后继、多块；复合 op 内联；切片简写降级

## 6 发射器扩展（oracle.emit_core）
- **区域与后继**：scf.if、scf.for 等带区域的 op 用通用形式发射，区域入口块写出块参数；cf.br、cf.cond_br 用 `[^块]` 列出后继，cond_br 自动补上分段属性；多块函数体照常发射。
- **透明复合 op**：先用 `core.inline_all` 内联再发射。不透明复合 op 仍然拒发，它们的类型事实由 compsig 的 Φ 负责。
- **切片简写降级**：
  - core 的 `extract_slice(t, offs, sizes)` 写成 MLIR 形式：`static_offsets`、`static_sizes` 全部取 kDynamic，`static_strides` 全为 1。
  - `insert_slice(s, t, offs)` 的尺寸取源的 extent：静态维直接写进 `static_sizes`，动态维插入 `arith.constant` 和 `tensor.dim`（这些 op 与原节点共用 loc）。
  - 降级之后，形状层的回归第一次全部经过了预言机：shape_test 调用 596 次，人工切片签名与预言机的分歧为 0。
- **参数归属守卫**：core 的参数只有在这个 op 的 MLIR 版本里也有对应属性时才翻译；op 是否有某个属性，直接取自 ODS 导入的属性表。

### 发现：core 的参数空间比 MLIR 大
edit_test 生成了带 `nuw` 的 `arith.xori`。core 的值层接受它，MLIR 却根本没有这个属性：xori 不带 `overflowFlags`。这个问题和第 7 轮发现的“手写方言语义”是同一类，只是这次出在参数上：**op 的参数集合也应当从 ODS 导入，而不是由 core 自己定义**。这一项归入下一轮的属性层。

### 导入修正
- `UnitAttr` 原来被当作必需属性，导致 scf.for 的 `unsignedCmp` 被误判为必需。修正后，可参与差分的 op 增加了 4 个。
- 新导入 ub 方言（`ub.poison`，core 里经常用到）。导入账变为：12 个方言，共 307 个 op，其中 auto 163、declared 135、unknown 9。差分：auto 6080/6080 一致，全体误拒 0。

## 7 检验
| 检验 | 结果 |
|---|---|
| O1 直线图（984 个） | 符号层 + 预言机与 MLIR **984/984** 一致；只用符号层时误拒 0、误收 49 |
| O5 区域/后继/多块图（1000 个，其中 488 个多块，带类型扰动） | 结构层 ∧ 类型层（含预言机）与 MLIR **1000/1000** 一致；不用预言机也是 **1000/1000**。拒绝的分布：结构层 493、符号层 249、预言机 0 |
| 回归测试中预言机不可用的次数（第 10 轮 → 第 11 轮） | core 598→2，shape 420→0，transform 175→15，loop 174→61，defs 110→59，edit 1074→465 |
| 回归测试中人工签名与预言机的分歧 | 0 |

- 剩下的不可用情形：edit 里的占位 op `edit.hole`（447 次）、模式变量与符号参数、core 的抽象类型 `memref`、option.* 定义层 op、memref.atomic_rmw（缺必需属性 kind）。

**L32：在随机分布下，区域与后继 op 的类型义务全部由结构层（R1–R8）和自动签名承担，预言机没有补上任何拒绝。** 也就是说，scf/cf/func 里写在 C++ 中的 verify 检查的是 yield/后继实参与结果类型、循环边界类型这类事实，结构层已经覆盖了。这是一个“没有发现”的结论，只在这个生成分布下成立：生成器没有覆盖 scf.while、scf.forall、scf.index_switch，也没有覆盖 func.call 的符号解析。
